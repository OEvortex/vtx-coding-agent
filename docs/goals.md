# Goals

A goal is a multi-turn objective with a task list, a verification contract, and an
independent audit before it can be closed, kept as markdown inside your project so it
survives restarts. This page covers the record format, the `goal` tool's actions, how
tasks and evidence work, what the auditor does, how two sessions share a goal, and the
dashboard.

## What a goal is

A goal is three things: an **objective** (what "done" means), a **task plan** (the steps
the agent tracks), and a **verification contract** (what will be checked). It is written to
`.vtx/goals/` in your project, so `git status` shows it and a teammate can read it.

The point is duration. A conversation ends when the session ends; a goal keeps the agent
pointed at the same outcome across restarts, compactions, and `/new`.

## Where goals live

```text
.vtx/goals/
  active_goal_<ts>_<id>.md        open goals
  archived/<same-name>.md         completed or killed goals
  ledger.jsonl                    durable activity ledger
  settings.json                   user settings (only written when changed)
  leases/<session_id>.json        live owner sessions
```

(`src/vtx/agent/goal/storage.py:3-9`)

The file name is built by `goal_filename` (`storage.py:71-75`): the creation timestamp
`[:19]` with `:`, `-`, and `T` normalised, then the 12-character goal id:

```text
active_goal_20261011-074313_7195939d6aed.md
```

`2026-10-11T07:43:13` becomes `20261011-074313`, so lexicographic order is chronological
order and the active pool is read oldest-first.

### The record

`GoalRecord` (`src/vtx/agent/goal/record.py`):

| Field | Type | Notes |
|---|---|---|
| `id` | `str` | `uuid4().hex[:12]` |
| `mode` | `"regular"` \| `"sisyphus"` | See the mode table below |
| `status` | `GoalStatus` | `active`, `paused`, `blocked`, `budget_limited`, `complete` |
| `objective` | `str` | Up to 4000 characters |
| `verification` | `str` | The completion contract |
| `prompt` | `str` | The prompt that created the goal |
| `tasks` | `list[TaskRecord]` | Nested via `parent_id` |
| `created_at`, `updated_at` | `str` | ISO-8601 |
| `revision` | `int` | Bumped on every mutation |
| `current_task_id` | `str \| None` | Explicit task pointer |
| `blocked_reason`, `paused_reason` | `str \| None` | |
| `completion_summary` | `str \| None` | What the agent claims it finished |
| `review_feedback` | `str \| None` | The auditor's objections |
| `token_budget` | `int \| None` | Total-token ceiling; `<= 0` is rejected |
| `usage` | `GoalUsage` | `input_tokens`, `output_tokens`, `elapsed_ms` |
| `session_id` | `str` | The owning session |

`GOAL_MODES`, `GOAL_STATUSES`, and `TASK_STATUSES` are the three enums
(`record.py:18-20`):

| Enum | Values |
|---|---|
| `GOAL_MODES` | `regular`, `sisyphus` |
| `GOAL_STATUSES` | `active`, `paused`, `blocked`, `budget_limited`, `complete` |
| `TASK_STATUSES` | `pending`, `complete`, `skipped` |

`is_open()` is true for four of the five statuses - everything except `complete`. The UI
labels them `running`, `paused`, `blocked`, `budget reached`, and `complete`
(`STATUS_LABELS`, `record.py`).

### The modes

| Mode | Meaning |
|---|---|
| `regular` | Open-ended. The task list is a plan, not a gate; the auditor checks the objective. |
| `sisyphus` | Strict sequential. The auditor is told "every numbered step must be satisfied in order, not just the last one" (`src/vtx/agent/goal/prompts.py:118-143`). |

```markdown
# Objective

Make `vtx plugin install` refuse an incompatible plugin with an actionable message

# Verification

uv run python -m pytest tests/plugins/ -q

# Tasks

- [x] t1  Add the version gate in plugin_cmd.py   --  uv run ruff check src/vtx/coding_agent/plugin_cmd.py
- [ ] t2  Print the exact remediation command
- [ ] t3  Cover both failure paths with tests
```

Read the structure (`src/vtx/agent/goal/storage.py:90-129`):

- The `<!-- vtx-goal:v1 --> ... -->` comment is the authoritative record, JSON at indent 1.
  It includes `objective` even though the body repeats it.
- The body is for humans: `# Objective`, then `# Verification`, `# Goal Prompt`, `# Tasks`,
  and `# Review Feedback`, in that order. Sections are omitted when empty.
- Task marks are `[x]` complete, `[-]` skipped, `[ ]` pending, with two spaces of indent
  per depth level. Completed tasks append their evidence; skipped tasks append
  `skipped: <note>`.
- **Edits to the `# Verification` body win over the metadata** when the metadata field is
  empty (`storage.py:153-155`). Rewrite the section in your editor and the change is
  picked up. Objective, status, and tasks come from the JSON, not the body.
- Writes are atomic: a temp file then `os.replace`. There is no window where a half-written
  goal file exists.

## The `goal` tool

`GoalTool`, name `goal`, icon `◈`, and **`mutating = False`**
(`src/vtx/agent/goal/tools.py:261-268`). That is deliberate: lifecycle bookkeeping on a
project-local markdown file does not need an approval prompt, while any destructive change
(unfocus) asks you first.

`GOAL_ACTIONS` (`tools.py:40-49`) is the accepted set:

| Action | Purpose |
|---|---|
| `create` | Create a goal and focus it |
| `get` | Snapshot the focused goal: objective, contract, tasks |
| `update` | Change status, revise the objective |
| `set_tasks` | Replace the task plan |
| `update_task` | Move one task, with evidence |
| `archive` | End the goal without completing it ("Goal archived (killed).") |
| `list_orphans` | List goals from sessions that are no longer running |
| `claim` | Take over an orphan |

### Parameters

`GoalParams` (`src/vtx/agent/goal/tools.py:190-258`):

| Field | Type | Used by | Notes |
|---|---|---|---|
| `action` | `str` | all | Required; unknown values return `action must be one of (...)` |
| `objective` | `str` (max 4000) | `create`, `update(revise)` | The complete outcome |
| `mode` | `str` | `create` | `regular` or `sisyphus` |
| `verification` | `str` | `create` | The contract or test command |
| `token_budget` | `int` | `create` | Total-token ceiling; must be `> 0` |
| `status` | `str` | `update` | `complete`, `blocked`, `paused`, `active`, `revise` |
| `reason` | `str` | `update` | Required for `blocked`; also revision notes |
| `completion_summary` | `str` | `update(complete)` | Submitted for audit, clipped to 2000 chars |
| `review_feedback` | `str` | `update` | Auditor objections to record |
| `tasks` | `list[GoalTaskItem]` | `set_tasks` | Replaces the plan |
| `task_id` | `str` | `update_task` | e.g. `t1`, or `t1.2` for a subtask |
| `task_status` | `str` | `update_task` | `start`, `complete`, `skipped`, `pending` |
| `evidence` | `str` | `update_task` | What proves the task is done |
| `note` | `str` (max 500) | `update_task` | Why a task was skipped |
| `subtasks` | `list[GoalTaskItem]` | `update_task` | Subtasks to attach |
| `goal_id` | `str` | `claim` | Orphan id to adopt |

`GoalTaskItem` (`tools.py:183-187`):

| Field | Type | Notes |
|---|---|---|
| `title` | `str` (1-300) | Not `text`; `title` is the field name |
| `id` | `str \| None` | Stable id like `t1` or `t1.1`; derived as `parent.n` when omitted |
| `parent_id` | `str \| None` | Parent task id for subtasks |
| `note` | `str` (max 500) | |

```json
{"action": "create", "objective": "Make the plugin install gate reject incompatible plugins", "verification": "uv run python -m pytest tests/plugins/ -q", "mode": "regular"}
```




## Tasks

`normalize_task_ids` (`src/vtx/agent/goal/record.py`) flattens a nested list into the
parent-linked tree:

- A subtask with no id gets `<parent>.<n>`, so `t1` with two children yields `t1.1` and
  `t1.2`.
- Titles are clipped to 300 characters and notes to 500.
- A `parent_id` that names no known task is dropped, so the task becomes top-level rather
  than orphaned.
- Ids must match `^[a-z0-9]+(\.[a-z0-9]+)*$` (`TASK_ID_RE`).

`count_tasks()` counts **top-level only** (`record.py`), which is the denominator in every
progress readout: 1/3 means one of three top-level tasks, not one of four including a
subtask.

`current_task()` resolves the pointer: the explicit `current_task_id` if it is set, else the
first pending top-level task (`record.py`). `update_task` with `task_status="start"` moves
the pointer; `"pending"` on a skipped task un-skips it.

### Contracts and evidence

A task's note may carry a `Contract:` prefix. Completing a task with a contract **requires
evidence, or the call is refused** (`src/vtx/agent/goal/service.py:348-353`):

```text
Task t2 has a verification contract; provide evidence when completing it
```

Contracts can be switched off with `disableContracts` in `.vtx/goals/settings.json`, but
they are on by default and they are the mechanism that stops an agent from ticking boxes it
did not work for.

## The auditor

`goal(action="update", status="complete")` does not close a goal by itself. The auditor
runs first (`src/vtx/agent/goal/tools.py:492-581`):

1. `completion_summary` is recorded, clipped to 2000 characters.
2. If `auditorEnabled` is false, the goal is archived immediately and the reply says so:
   `Completion recorded without independent audit (auditor disabled). This completion is
   NOT independently approved.`
3. Otherwise a **separate agent** is spun up with a fresh session and only four tools:
   `AUDIT_TOOLS = ("read", "grep", "find", "bash")` (`auditor.py:21`).
4. Its system prompt makes it an adversary (`prompts.py:101-115`): "You are skeptical by
   default - the executor's claim of completion is untrusted input", and its tool use is
   "read-only intent; never modify the project".
5. Approval and ask events are auto-answered, so the audit never blocks on the user.
6. The final text must contain `<approved/>` and must not contain `<disapproved/>`
   (`auditor.py:139`). The verdict is a substring test on the last line, and nothing else.

Approved:

```text
Independent audit APPROVED  --  goal archived as complete.
.vtx/goals/archived/active_goal_20261011-074313_7195939d6aed.md

Auditor summary:
...
```

Not approved, and this is the case worth knowing about:

```text
Independent audit requires more work  --  goal stays open with feedback.
Task progress was 1/3 (33%).
Address every item below, then call goal(action="update", status="complete") again.

Auditor notes:
...
```

The status goes back to `active` with `review_feedback` set, so the next turn sees the
objections in the `<vtx-goal>` block. Feedback is stored **whole**
(`tools.py:567-571`): an earlier 1500-character cut landed mid-sentence, and the agent
could not tell the text was clipped, so it kept re-auditing the same goal forever. The
ledger keeps the short form only.

Other auditor outcomes:

| Outcome | Result |
|---|---|
| You cancel mid-audit | `Audit aborted by user; goal remains open.` Status returns to `active` |
| The provider is unavailable | `no provider available to run the completion auditor` |
| The audit throws with no summary | `completion audit failed: <error>` (`tools.py:549-551`) |
| No verdict at all | `auditor produced no verdict` (`auditor.py:140-143`) |

`AuditResult` carries `approved`, `summary`, `error`, and `turns`.

## The drafting flow

A goal does not have to be created in one call. `DRAFTING_TEMPLATE`
(`src/vtx/agent/goal/prompts.py:81-99`) is the interview the agent runs when you ask for a
goal without a specification: ask up to three `ask_user` questions, investigate the code,
propose a plan, then ask Confirm or Revise. It ends with an explicit constraint:

```text
Only after explicit confirmation create the goal with `goal(action="create",
objective=...)`. Never create the goal before confirmation.
```

The agent also cannot create a second goal while one is focused. `_create` refuses with
(`tools.py:382-390`):

```text
This session already focuses on an open goal: 'Make the plugin install gate ...'.
Finish it or ask the user to archive/unfocus first.
```

One goal, one session, at a time.

## The context block

While a goal is focused, `goal_context_block` is prepended to every user prompt
(`src/vtx/tui/commands/goals.py:226-233`). This is the real output for the goal above:

```text
<vtx-goal>
Focused goal (regular): Make `vtx plugin install` refuse an incompatible plugin with an actionable message
Status: running [0m00s 0]
Tasks: 1/3 complete (33%)
Current task: [t2] Print the exact remediation command
Track progress with goal(action="update_task"); finish only via goal(action="update", status="complete") which triggers an independent audit.
</vtx-goal>
```

The block carries elapsed time and token usage when there are any, the task counts and
percentage, the current task with its subtask progress, and any auditor feedback. It is
what makes a goal survive compaction: the model re-reads the objective every turn instead of
remembering it.

`continuation_prompt` (`prompts.py:65-99`) is the auto-continue prompt when you leave a goal
active and come back:

```text
<vtx-goal-continue>
Goal checkpoint. Re-read the focused goal state above and take the next
concrete step toward it (mode: regular). Work on the current task; mark
progress with goal(action="update_task") as you go.
Do not rush, skip steps, or invent preflight work. If the objective is
genuinely satisfied, call goal(action="update", status="complete").
If you are truly blocked after real attempts, call
goal(action="update", status="blocked", reason="...").
</vtx-goal-continue>
```

In the UI that prompt is shown as `◈ goal checkpoint · <title>`. Pressing Escape while a
goal is active **pauses** it (`_pause_goal_on_interrupt`, `goals.py:250-263`), which is why
an interrupted goal session resumes cleanly.

`charge_goal_usage` fires after each turn (`goals.py:265-286`). When
`usage.total_tokens()` reaches `token_budget`, the status flips to `budget_limited` and the
UI announces it. A new session starts with no `vtx-goal-focus` entry, so it comes up
unfocused without touching the goal file.

## Persistence and ownership

Every mutation goes through one pipeline (`src/vtx/agent/goal/service.py:3-13`):

```text
reconcile (disk wins over stale memory) → validate → mutate a clone (never the live
object) → write or archive the active file → append ledger events (best-effort) →
publish the new record. If the write fails, nothing commits and nothing is appended.
```

The important part is the clone: the in-memory record is never edited in place, so a failed
write cannot leave the service and the file disagreeing. Each `mutate` bumps `revision` and
`updated_at`.

`GoalService` is cached per `(cwd, session_id)` (`service.py:439-449`), and it reconciles
from disk on every read, so an edit you make by hand is picked up.

### Leases and other sessions

A goal belongs to a session. `leases/<session_id>.json` marks an owner as live, with
`LEASE_TTL_SECONDS = 120` (`storage.py:40`). `live_sessions` returns ids whose lease file
was modified within the TTL; a missing lease only makes a goal look claimable, never lost.

| Method | Behavior |
|---|---|
| `claimable()` | Open goals whose owner is not live and is not you (`service.py`) |
| `claim(id)` | Take one over; refuses if the owner is running: `Goal <id> belongs to another running vtx session; wait for it to exit before taking it over` |
| `list_orphans` | The tool's view of the same list, sorted by creation |
| `set_focus(id)` | Always writes a `focus_changed` ledger event, even for a no-op |
| `unfocus()` | Clears focus |

Focus persists as a `vtx-goal-focus` custom session entry
(`src/vtx/tui/commands/goals.py:137-160`), so a restarted session re-focuses the same goal,
and `_resolve_startup_focus` auto-focuses the sole open goal when `autoSelectSingleGoal`
is on.

### The ledger

`ledger.jsonl` is one JSON object per event, append-only, best-effort - `append_ledger`
returns `False` on `OSError` rather than failing the mutation. Real lines:

```json
{"ts": "2026-10-11T07:43:13+00:00", "type": "created", "goal_id": "7195939d6aed", "mode": "regular", "source": "goal-doc", "session_id": "sess-demo"}
{"ts": "2026-10-11T07:43:13+00:00", "type": "task_updated", "goal_id": "7195939d6aed", "task_id": "t1", "status": "complete"}
```

`recent_activity(cwd, goal_id=None, limit=8)` turns them into lines with verbs from
`ACTIVITY_VERBS` (`storage.py:335-379`), newest first, clipped to 140 characters:

```text
2026-10-11 07:43:13 · task t2 → start
2026-10-11 07:43:13 · task t1 → complete
2026-10-11 07:43:13 · task list set
2026-10-11 07:43:13 · focused
2026-10-11 07:43:13 · created
```

## Settings

`.vtx/goals/settings.json`, read into `DEFAULT_SETTINGS` (`storage.py:381-405`). The file
is optional and is only written when a value changes; unknown keys and non-boolean values
are ignored on load.

| Key | Default | Effect |
|---|---|---|
| `disabled` | `false` | `create` and `update` refuse: `The goal system is disabled in settings` |
| `autoContinue` | `true` | Auto-continue an active goal on the next turn |
| `disableTasks` | `false` | `set_tasks` and `update_task` refuse: `Task lists are disabled in settings` |
| `disableContracts` | `false` | Completion no longer requires evidence on a contracted task |
| `auditorEnabled` | `true` | Skip the independent audit (see the warning above) |
| `autoSelectSingleGoal` | `true` | Focus the only open goal at startup |

```json
{"disabled": false, "autoContinue": true, "disableTasks": false, "disableContracts": false, "auditorEnabled": true, "autoSelectSingleGoal": true}
```

## The dashboard

Two widgets, both in the TUI.

**The beacon** (`GoalWidget`, `src/vtx/tui/goal_ui.py:726`) sits above the editor and shows
the focused goal, its status, and the next few tasks. Task marks are
`✓` complete, `▸` current, `~` skipped, `·` pending (`TASK_MARKS`, `goal_ui.py:79`), with
5 visible task rows, 3 subtask rows, and 2 sub-agent rows.

**The dashboard** (`GoalDashboardScreen`, `goal_ui.py:1194-1273`) is a modal opened with
`ctrl+shift+g` (`src/vtx/tui/app.py:92`). `escape` closes it, and it re-renders every
`TICK_SECONDS = 1.0` so elapsed time and token counts move while you watch, capped at
`MAX_WIDTH = 120`.

There is no `/goal` slash command. Command handling was removed in favour of the builtin
`goal` skill (`src/vtx/tui/commands/goals.py:3`), which is the drafting flow above. The
`goal` tool itself is what the model calls.

## Complete example

Everything above, in one flow. Create the goal, plan it, work it, and close it:

```json
{"action": "create",
 "objective": "Make `vtx plugin install` refuse an incompatible plugin with an actionable message",
 "verification": "uv run python -m pytest tests/plugins/ -q",
 "mode": "regular",
 "token_budget": 250000}
```

```text
Goal created and focused.
Goal 7195939d6aed (regular)
Status: running [0m00s 0]
Tasks: 0/0
Objective: Make `vtx plugin install` refuse an incompatible plugin with an actionable message
File: .vtx/goals/active_goal_20261011-074313_7195939d6aed.md
Begin working toward the objective now.
```

`_snapshot_text` never truncates the objective, contract, or auditor feedback - "a silently
clipped verdict is what makes an audit loop unfixable" (`tools.py:99-127`).

```json
{"action": "set_tasks", "tasks": [
  {"id": "t1", "title": "Add the version gate in plugin_cmd.py",
   "note": "Contract: gate returns exit code 2 and names the required version"},
  {"id": "t2", "title": "Print the exact remediation command"},
  {"id": "t3", "title": "Cover both failure paths with tests"}
]}
```

```json
{"action": "update_task", "task_id": "t1", "task_status": "start"}
```

```json
{"action": "update_task", "task_id": "t1", "task_status": "complete",
 "evidence": "uv run python -m pytest tests/plugins/ -q -k incompatibility  ->  2 passed"}
```

That evidence is required, because `t1` carries a `Contract:` note; the same call without
`evidence` is refused. Move the pointer off a finished task with `task_status="start"` on
the next one; `update_task` reports what the pointer moved to:

```text
Task updated: [t1] Add the version gate in plugin_cmd.py → complete
Progress: 1/3 (33%)
Current task now: [t2] Print the exact remediation command
```

Close it, and expect the loop to possibly run twice:

```json
{"action": "update", "status": "complete",
 "completion_summary": "The gate now exits 2 with the remediation command, and both failure paths have tests."}
```

If the auditor disagrees you get `changes required ✗`, the status stays `active`, and the
feedback is in the `<vtx-goal>` block on the very next turn. Address it, then call
`complete` again. To give up instead of finishing:

```json
{"action": "archive"}
```

```text
Goal archived (killed).
.vtx/goals/archived/active_goal_20261011-074313_7195939d6aed.md
```

Archiving moves the file to `.vtx/goals/archived/` and is the one destructive step in the
system, which is why it is a separate action from `update`.

## Known gaps

- **There is no `/goal` slash command.** The dashboard is `ctrl+shift+g`; goal manipulation
  is the `goal` tool and the builtin `goal` skill (`src/vtx/tui/commands/goals.py:3`).
- **Three goal pickers are wired but never opened.** `SelectionMode.GOAL_FOCUS`,
  `GOAL_CLEAR`, and `GOAL_SETTINGS` are defined (`src/vtx/tui/selection_mode.py:23-25`) and
  handled (`src/vtx/tui/completion_ui.py:256-261`), but nothing raises them, so there is no
  in-TUI way to switch goal, archive with confirmation, or toggle a setting. Edit
  `.vtx/goals/settings.json` by hand, call `goal(action="archive")`, or start a session with
  no focus entry.
- **`GoalParams.action`'s own description omits `archive`** (`tools.py:191-196`). The action
  *is* accepted - it is in `GOAL_ACTIONS` and in the dispatch table - so a model that trusts
  the description will not find it.
- **The `goal` row in `tools.md` is missing the task fields.** Its parameter table lists
  `action`, `objective`, `mode`, `verification`, `token_budget`, and `status`, and its
  `action` description duplicates `update` where `archive` belongs. It omits `reason`,
  `completion_summary`, `review_feedback`, `tasks`, `task_id`, `task_status`, `evidence`,
  `note`, `subtasks`, and `goal_id`, and its `set_tasks` example uses a `text` key where the
  field is `title`. The table above is the complete set.
- **Only one focused goal per session, and focus is not lockable.** A second `create` is
  refused, but nothing stops two sessions from claiming the same goal if the owner's lease
  expires - 120 seconds with no renewal is enough.
- **The auditor is read-only by instruction, not by construction.** It gets `bash` and is
  told "never modify the project" (`prompts.py:101-115`); a rogue model that writes anyway
  will not be stopped by the harness.
- **An audit needs a provider.** In a headless run with no model available, `complete`
  fails with `no provider available to run the completion auditor` rather than degrading to
  an unaudited completion.
- **`token_budget` stops charging, not working.** Hitting the cap flips status to
  `budget_limited` and announces it; the agent keeps going until the session ends or the
  goal is unfocused.
- **The ledger can lose events.** `append_ledger` is best-effort and returns `False` on
  failure, so a read-only filesystem silently drops history while the goal file still updates.
